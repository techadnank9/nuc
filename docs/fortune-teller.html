The Robot Fortune Teller

Ask a question out loud. Two robot arms draw a card from the deck, reveal it to you, and a voice reads your fortune. If its hands fail, it asks you for help, in character.

ContextThe hackathon

A weekend at Founders Inc in San Francisco, about 200 builders, building AI that acts in the physical world. Hosted by MakerMods, Dream Labs and LiveKit.

Arms

MakerMods

Bimanual 6-axis arms with parallel grippers. Creative teams use the Maker Arm stations; ours is NUCK-8.

Brain

Dream Labs, Dream-1

A "world action model": send camera frames, the arms' state and a task in plain words, get back about 1.6 s of arm motion. It can be fine-tuned on your own demonstrations.

Voice

LiveKit

Real-time audio and video, plus a voice agent framework: speech in, an LLM in the middle, speech out, with tools the agent can call.

ConceptThe idea

A screen can pick a random card. It cannot draw one. The physical draw (hand reaching into the deck, a card rising into view) is the ritual people come for. That makes the arm the point, not decoration.

Design rule

One motion, done perfectly

Dream-1 is a learned policy: every extra task or variation needs more demonstrations and lowers reliability. So the arm does exactly one thing, the same way every time: draw the front card and place it in the stand.

Where the magic comes from

Randomness lives in the deck

The deck sits in a gravity-fed tray, so the front card is always in the same place. The guest shuffles. The robot never has to choose, only to draw.

Technical viewHow it works

Three pieces talk to each other: a voice agent on the laptop, a small "harness" program that runs the robot, and the station computer (NUCK-8) that drives the arms and cameras with Dream-1.

Laptop

Voice agent

LiveKit Agents (Python). One tool, draw_card(). A short prompt keeps the fortune teller theatrical but brief, and a card-meanings table keeps readings grounded in the card actually drawn.

Laptop

Harness

Wraps the robot in one function. It checks the arms are free, starts Dream-1 over SSH, stops it on a time budget, then reads which card landed in the stand from the overhead camera.

Station

Dream-1 run

dreamcli robot run --task "draw the front card from the deck and place it in the stand", using our fine-tuned model once it is trained.

Technical detailThe draw loop, with verify and recover

The organizers' advice for both tracks: check every action, retry a limited number of times, and fall back gracefully. Here that becomes the "I am stuck" moment.

Why the run is time-boxed: when a Dream-1 run stops, the arms return home and go limp. The card must already be in the stand by then, and the cameras only become free for reading the card once the run has stopped.

Robot learningTeaching the arm

Dream-1 can run without training, but on our Maker Arms its moves don't yet match what we want. Fine-tuning on our own demonstrations is what makes the draw reliable.

1 · Record

50 to 60 demos

Drive the right arm with the Meta Quest controllers (dhk-collect). Same task text every time, 15 to 25 s each, plus 8 to 10 "recovery" demos with a crooked card.

2 · Prepare

Add tool poses, check

tools/add_eef.py adds the gripper poses Dream needs, and finetune.py --check validates the dataset locally, for free.

3 · Train

Queue by 9 pm

A fine-tune takes 7 to 8 hours plus queue time, and the first start can take up to an hour. Queue tonight, test tomorrow morning. Costs credits: confirm with the organizers first.

What's already proven today

  • Dream-1 inference works from NUCK-8 with our key: the base model answered 2 of 2 calls on a recorded demo.
  • All three cameras and the Quest are recognized by the station; both arm links come up.
  • Card v1 is modelled, checked (watertight, correct grip spacing) and ordered.
Blocker before any live run: the station's Dream config still describes YAM arms. dreamcli setup must be rerun for Maker arms first.

Safety, every live run

One person on the emergency stop and nobody within reach of the arms. Arms resting where they can go limp before every start and stop. A dry run first after any config change.
